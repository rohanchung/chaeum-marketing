# 채움 마케팅 구현·검증 기록

2026-09-13. HANDOFF-ASTRA 이후 로한의 개발 승인과 채널 지표→학원 퍼널→수익성 요구에 따른 변경이다.

## 데이터와 계산

| 대상 | 저장·집계 |
| --- | --- |
| 채널 지표 | `mkt_metrics` 정의 + `mkt_values`의 지표·소재·집행·날짜별 독립 값 |
| 광고 집행 | 같은 소재에 기간이 다른 여러 `mkt_promotions` 연결 |
| 마케팅 비용 | `mkt_costs`의 지급 완료액. 표의 광고비와 원장은 같은 기록 |
| 고객 전환 | `mkt_customers`의 최초 상담일, 등록일, 확인 근거와 주 출처 |
| 수납·환불 | `mkt_payments`의 실제 결제일·원거래 연결·서비스 원가 |
| 기간 보고 | 화면·Excel·인쇄가 `analytics.ts`의 같은 Report 사용 |

누적값은 마지막 관측이며 최대값·누적 합계가 아니다. 비율은 원시 합계로 재계산한다. 0과 미입력은 구분한다. 원가가 비어 있으면 ROI를 계산하지 않는다. 객단가는 기간 순수납을 양수 결제한 고유 고객 수로 나눈다. 연간 객단가를 월별 객단가 평균으로 만들지 않는다.

일일 전체 퍼널과 개별 고객 표본은 합치지 않는다. 출처 미확인·운영자 추정 고객의 매출을 특정 채널에 귀속하지 않는다. 채널·소재·집행은 중첩된 조회 수준이므로 각 수준의 행을 다시 합산하지 않는다.

## 검증

- TypeScript, ESLint 및 GitHub Pages 하위 경로의 정적 빌드 통과.
- 자동 계산·내보내기 테스트 15개: 독립 지표, 누적 정정, 누락과 0, 가중 비율, 환불, 객단가, 원가 누락, 미지급 제외, 삭제 시 원장 보존, 상담 코호트, 귀속 근거, 연간 고유 고객, 출력 문자 이스케이프, 음수 현금 흐름, Excel 숫자·빈칸 보존.
- 실제 로그인 역할 DB 검사: CRUD, 다중 셀 저장 원자성, 광고 기간, 지표 의미 변경 방지, 비용 중복 방지, 초과 환불 차단, 수명주기 및 백업 복원 통과. 모든 검사 기록 롤백.
- 권한 검사: 작업공간 간 격리, 복합 외래키, 조회 전용 역할의 쓰기 차단, 외부 사용자·익명 접근 차단 통과.
- 로그인한 브라우저: 새 채널·소재·집행 생성, 직접 입력·2×2 붙여넣기·재조회, 광고비 저장, 고객 주 출처·등록·수납·환불 저장, 월간·연간 ROI/객단가, 비용 이름·메모 보존, 보고 시점 저장, 아카이브·운영 복원·휴지통 이동 확인.
- 브라우저 예시: 비용 10,000원, 수납 300,000원, 원가 100,000원 → ROI 1,900%; 환불 30,000원 추가 → 순수납·객단가 270,000원, ROI 1,600%.
- 위 브라우저 검증에서 생성한 채널·소재·집행·지표값·고객·수납·환불·비용·보고서는 검증 후 해당 ID만 지정해 정리했다. 기존 운영 기록과 감사 이력은 유지했다.
- 인쇄 HTML과 Excel 직렬화는 자동 검사했다. Codex 미리보기에서 Excel 버튼 클릭 후 앱 오류는 없었으나 다운로드 이벤트를 받지 못해 브라우저의 실제 파일 저장 완료는 확인하지 못했다. OS PDF 저장 대화상자 및 브라우저 파일 선택을 통한 JSON 복원도 수동 확인하지 않았다. 복원 RPC 자체는 DB에서 검증했다.

## 적용 및 운영

Supabase 프로젝트 `nwxbfmycimrxaovemela`에 다음 5개 마이그레이션을 적용했다. 파일 버전을 원격 이력에 맞춰 정리했다.

1. `20260911065100_marketing_measurement_and_roi.sql`
2. `20260911095337_marketing_integrity_and_restore.sql`
3. `20260911095935_marketing_templates_and_guards.sql`
4. `20260911100223_fix_marketing_validation_dispatch.sql`
5. `20260913074739_marketing_lookup_indexes.sql`

원격 DB의 초기 스키마는 기존에 수동 적용됐지만 migration history에 없다. 초기 스키마 재실행이나 무조건적인 `db push` 대신 기준 이력 정리가 먼저다. 신규 테이블 RLS와 쓰기 검증을 적용했으며, 보안 검사에는 기존 Auth의 [유출 비밀번호 차단 비활성화](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) 경고 1건이 남는다. 별도 서비스 설정은 변경하지 않았다.

현재 규모에서는 전체 작업공간 데이터를 1,000건 단위로 끝까지 조회한다. 다수 학원의 장기 대용량 운영 단계에서는 기간 조회와 서버 집계로 확장해야 한다. 자동 채널 수집·자동 외부 백업·누적 지표의 경계 증가분 계산은 현재 구현 범위에 포함하지 않는다.

백업은 현재 앱 테이블을 같은 작업공간에 병합 복원한다. 백업에 없는 행을 삭제하지 않는다. 종전 테이블과 감사 로그는 보관용으로 함께 내보내며 복원 대상은 아니다. 서비스 외부의 영구 무손실 보존을 보장하지 않는다.
